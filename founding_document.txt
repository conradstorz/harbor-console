Harbor Console

Vision

Harbor Console is a lightweight operational console for a small fleet of Linux
servers.

Its purpose has two halves:

Replace the default Linux login console with a useful operational dashboard.

Be the authority on which services run, on which host and port, and whether
they are up.

The first half shipped as v0.1.0 and is unchanged. The second half was added
after a real operational need was demonstrated: two projects both published
host port 8080, and nothing in the system would have said so. The collision
would have surfaced only as a dashboard that quietly never appeared.

Two surfaces, one core.

harbor-console

Runs on tty1 at the attached monitor. Answers "is my server healthy?"

harbor-console-web

Runs continuously under systemd. Answers "what is running, where, and is it
up?" for anyone on the tailnet.

Their lifetimes are independent. Logging in at the attached monitor must not
take the tailnet page down, and the tailnet page must not depend on anyone
being logged in.

v0.2.0 - Service Registry and Tailnet Status Page

The Registry

The registry is two kinds of file, not one, because what a project wants and
what it holds are different facts.

.harbor.toml - one per participating project, living in that project's own
repository and owned by whoever works there. It declares:

project - the project's name

host - which machine it deploys to

and one [[port]] block per published port:

name - the port's name within the project; the environment variable it is
published through is derived from it

want - the number this project would like

assigned - the number it got; written by harbor-console, never hand-edited

container - for reconciliation against Docker

health_path - accepted and ignored. The web surface holds the ledger and never
a declaration, so it probes / by convention on every leased port; any HTTP
response means up. See ADR 12.

hcstatus_path - accepted and ignored, for the same reason. The web surface
fetches /hcstatus by convention; it is optional, adds richer status detail, and
never affects up or down.

description

services.toml - the ledger. One file, version controlled in this repository and
deployed with it. It is diffable and reviewable because it is an authority, not
a cache, and it is written only by harbor-console ports sync. Each entry
records one granted lease:

project - who holds it

name - which of that project's declared ports

host - present from day one, so a second machine is a data change and not a
rewrite

addr - the bind address the port is published on

port - the published host port number; the lease owns it

granted - the date the lease was issued, which is what settles a conflict

A project's want is a request. The lease is the answer. You do not always get
what you asked for, which is why the two are recorded separately.

Three rules make the ledger an authority rather than a list:

(host, addr, port) is unique. A duplicate is a hard error when the file loads,
not a warning. This is the 8080 collision caught at edit time. The bind address
is part of the key because an address-scoped publish is a real and distinct
claim: 0.0.0.0 is the wildcard and contends with every address on its host, two
different specific addresses on one host do not contend with each other, and
two different hosts never contend at all. That is how a container published
to one specific address keeps 100.69.239.123:49152 without claiming 49152
from everyone else. See ADR 10.

Every service is declared, including harbor-console-web itself. It takes its
port from the same file it serves.

Declaring is not deploying. The file records intent. Docker holds reality.

Opting in is a small, local change in the project itself: add a .harbor.toml,
and read the port from the variable in the compose file. Nothing else about
another project has to change for it to appear in the ledger.

Reconciliation

The page shows declared state beside live Docker state and names the three
ways they disagree:

Declared but not running.

Running but not declared.

Running on a port that does not match the declaration.

The third is the failure mode that motivated this release.

Health Probing

Deliberately dumb. Connect, and any HTTP response means up.

A service answering / with a 303 redirect to /login is a healthy service. A
probe insisting on 200 would call it down, and a status page that cries wolf
is worse than no status page.

The probed paths are fixed by convention: / for liveness and /hcstatus for
optional detail, on every leased port. The server holds the ledger and never a
project's .harbor.toml, so no project can choose its own. See ADR 12.

A leased port that is held but does not answer an HTTP probe shows as
LISTENING, not DOWN. That is the correct state for a service that does not
speak HTTP - ice-colder's MQTT broker on 1883 - and DOWN is reserved for a
leased port with nothing listening on it at all.

The Web Surface

Binding is the access control. harbor-console-web binds the host's Tailscale
address only. Never 0.0.0.0. If the Tailscale interface is not up, it refuses
to start and lets systemd retry. There is no fallback bind, because a silent
fallback would publish an inventory of every service on the host to the whole
LAN. There is no login page; the network is the gate. See ADR 7.

Standard library http.server. No FastAPI, no uvicorn, no new runtime
dependency. One self-contained page.

Probing happens in a background thread, never inside a request. The page
renders last known results with a timestamp. The page that exists to tell you
something is wrong must not become the thing that is wrong.

The page shows three things: server health (the same metrics as the terminal
console), the service directory with live or down state, and the drift list.
It auto-refreshes on a timer.

The host it serves is decided once, at startup, from the lease this process
holds in the ledger - never from the operating system's hostname. The ledger's
host is a hand-authored string, and a name that disagrees with the OS (hpz440
against hpz440.lan) would silently empty this host's share of the ledger and
report every healthy container as undeclared.

It therefore also refuses to start when its own service is declared more than
once in the ledger. Running one page for several hosts needs an explicit choice
of identity, and that choice is deferred rather than guessed.

The same page serves /ports.json, the authoritative host state the allocator
reads. Until the first probe cycle completes it answers 503, not an empty
listing: a snapshot nobody has filled in has no listeners because none were
looked for, and serving that as success would let the allocator grant a port
that is already in use. It answers 503 again whenever Docker could not be
read: the sockets are real but nothing can be attributed to a container,
which is just as dangerous a success response.

The page is read only. No buttons that do anything. Port allocation authority
was chosen over lifecycle control, so nothing here can start or stop a
container.

Links are built from each entry's host and port. Tailscale MagicDNS resolves
the name from anywhere on the tailnet, which is why no discovery protocol is
needed. mDNS was considered and rejected: it is link local and does not cross
a tailnet, which is precisely the case it was wanted for.

What gatekeeping means

Port allocation authority only. Not lifecycle control. Not access control.

There is no registry.py. Reading and validating services.toml is ports/ledger.py,
and it is one half of a pair: a project's own .harbor.toml is read by
ports/declaration.py. Everything listed here is shipped: the allocator under
ports/, and the eight modules of the web surface - tailnet.py, listening.py,
docker.py, probe.py, reconcile.py, snapshot.py, web.py and webapp.py.

Initial Features

system.py

Responsible for collecting:

hostname

uptime

CPU usage

memory usage

disk usage

IPv4 address

Docker container count

ports/

The port allocator, and the same split applied again - collect, decide, render,
coordinate.

keys.py, ledger.py and declaration.py collect: the ledger of granted leases, and
each project's declaration of what it wants. A ledger that claims one
(host, addr, port) twice is rejected when it loads. Collecting only; no
rendering, no probing.

live.py, discovery.py and compose.py collect host state: what is listening on
the target host, which projects in the tree participate, and what each compose
file publishes.

allocate.py decides. It is pure - no I/O at all - so every allocation rule is
testable with plain values.

envfile.py and explainer.py render the two generated artifacts: the managed
fence in a project's .env, and HARBOR_PORTS.md.

atomic.py is the one way a whole file is replaced: a temp file beside the
target, then a move over it.

cli.py coordinates scan, sync and show, and is the only module in the allocator
that writes. scan reports and writes nothing. sync applies decisions, and also
repairs a project whose own .env fence or HARBOR_PORTS.md has drifted from the
lease it already holds - a fresh clone has no .env, and without the repair its
compose file would fall back to a default that may collide. show reads the
ledger alone, so a broken declaration somewhere in the tree does not stop an
operator reading the lease table.

tailnet.py

Reports the host's Tailscale address, asking tailscale itself rather than
guessing from an interface or an address range. The one collector in this
project that raises instead of degrading: a silent fallback here would publish
the whole directory to the LAN. See ADR 7.

listening.py

Reports every listening TCP socket on this host, including loopback-bound and
non-Docker ones that Docker cannot see. A socket bound to IPv6 :: is normalised
to 0.0.0.0, the wildcard the ledger's overlap rule knows.

docker.py

Reports live container state for reconciliation. Degrades to empty rather than
raising when Docker is unavailable - and reports that it could not ask Docker
at all as a distinguishable result, because "nothing is running" and "nobody
answered" must not both read as an undeclared fleet.

probe.py

Probes one service: / for liveness, /hcstatus for optional detail, both by
convention rather than from a declaration the server does not have. See ADR 12.

reconcile.py

Decides where the ledger and reality disagree. Pure - no I/O - for the same
reason allocate.py is. Joins leases against listeners and published container
ports on (addr, port), compared by address overlap.

snapshot.py

The contract between the prober and the renderer, and data only. Its own module
so neither side imports the other, the way ports/keys.py serves the allocator.
It records whether a cycle has ever completed, and why the last one failed.

ui.py

Responsible only for rendering the terminal dashboard.

No business logic.

web.py

Responsible only for rendering the HTML page and serving it.

No business logic, no collection.

app.py

Coordinates the terminal refresh loop.

Refresh interval:

1 second

webapp.py

Coordinates the web service: the background prober and the HTTP server. Every
refusal lives here and happens at startup - no Tailscale address, no readable
ledger, no lease of its own, or more than one lease that could be its own. It
ships as its own systemd unit, deploy/harbor-console-web.service, installed
alongside the tty1 unit by deploy/install.sh.

Collect, render, and coordinate stay separate. A web view is a second renderer
over the same collectors, not a second application.

Release Criteria

v0.1.0 is complete when:

It automatically starts.

It continuously updates.

It never crashes during normal operation.

The Linux login console is no longer preferred.

v0.2.0 is complete when:

services.toml declares every service on the host, including harbor-console-web.

A duplicate (host, addr, port) fails loudly rather than shipping.

The page is reachable from anywhere on the tailnet and from nowhere else.

The page loads promptly even when a declared service is hung.

Drift between declaration and Docker is visible without logging into the host.

Both units survive each other: restarting one does not disturb the other.

Open Questions

Both questions this section once posed have been decided and recorded as
ADRs; none remain open.

How the port authority is enforced was decided on 2026-09-01: by allocation.
Projects declare what they need in .harbor.toml, harbor-console leases a port and
writes it into the project's .env, and the incumbent always keeps what it holds.
See ADR 8.

Where the registry lives on disk was decided on 2026-09-02: it stays in
repository, deployed to /opt/harbor-console/services.toml by the installer.
See ADR 13.

Definition of Success

Two questions, each answered in under five seconds.

At the attached monitor: "Is my server healthy?"

From anywhere on the tailnet: "What is running here, and is it up?"

If both answers are obvious at a glance, the console has achieved its purpose.
